# Yani CRM — план реализации

Цель: добавить в Yani локально тестируемую мини-CRM для продаж через Telegram и email. Каждая фаза сначала принимается на локальном стенде; production-деплой выполняется отдельно после подтверждения.

## Базовые решения

- CRM изолируется по `agentId`; организация видит только CRM своего агента.
- Пользовательский «Навык продажи» реализуется отдельной сущностью `SalesPlaybook`, а не перегружает существующий общий `Skill`.
- У каждого playbook собственные документы, лиды, история и состояние `RUNNING / STOPPED`.
- Существующий `AgentEngine` переиспользуется, но получает отдельный sales-контекст и источники.
- CRM-сообщения не хранятся в `ChatMessage`: у него другой срок хранения. Для CRM создаются постоянные `Conversation` и `CrmMessage`.
- Исходящие проходят через persistent outbox. LLM никогда не отправляет сообщение прямо в Telegram или SMTP.
- На первом этапе все исходящие требуют подтверждения. Автоматическую отправку включаем отдельной настройкой позже.
- SQLite остаётся для локального MVP. Redis/BullMQ подключается с момента появления каналов и фоновой доставки.
- Секреты каналов не попадают в промпты и логи. В production их нужно шифровать или вынести в secret storage.

## Ограничения каналов

- Telegram Bot API не может первым написать произвольному username. Клиент должен сначала открыть бота и отправить сообщение.
- Для первого контакта в Telegram возможны: ссылка на бота, Telegram Business connection или отдельное согласованное решение. Userbot не закладывается из-за риска блокировок и нарушения правил.
- Email может писать первым, но массовые отправки требуют согласия, throttling, корректной SPF/DKIM/DMARC-настройки и возможности остановки.

## Целевая модель данных

### SalesPlaybook

- `id`, `agentId`, `name`, `product`, `systemPrompt`, `goals`
- `communicationStyle`, `restrictions`, `status`
- `sendMode`: `DRAFT_ONLY`, `APPROVAL_REQUIRED`, `AUTO`
- уникальность имени внутри агента

### SalesDocument

- `playbookId`, имя, MIME, путь, извлечённый текст, порядок
- форматы MVP: DOCX, PDF, PPTX
- лимиты размера и текста; ошибки извлечения показываются в UI

### Lead и идентификаторы

- `Lead`: playbook, стадия, имя, компания, email, телефон, Telegram, заметки, индивидуальная инструкция
- `LeadIdentity`: тип + нормализованное значение
- уникальный ключ: `playbookId + type + normalizedValue`
- один контакт может существовать в разных playbook, но не дублируется внутри одного

### Диалоги и сообщения

- `Conversation`: lead, channel, external thread/chat id, режим автопилота
- `CrmMessage`: direction, status, text, attachments, external id, timestamps
- все сообщения Telegram и email отображаются в одной хронологии карточки

### Каналы и очереди

- `ChannelConnection`: playbook/agent, тип, состояние, публичный config, encrypted secret reference
- `InboundEvent`: уникальный внешний id, payload, processing status
- `OutboxMessage`: draft/approval/sending/sent/failed, attempts, next attempt
- уникальные idempotency keys защищают от повторной отправки

## Стадии канбана MVP

1. Новый контакт
2. Идёт общение
3. Клиент хочет заказать
4. Клиент
5. Архив

Drag-and-drop не будет единственным способом: в карточке также будет меню смены стадии для мобильных устройств и клавиатуры.

## Фазы

### Фаза 1 — CRM-ядро без внешних каналов (3–5 дней)

Делаем:

- новый раздел CRM в кабинете организации и админке;
- канбан с пятью стадиями;
- создание/редактирование карточки;
- профиль клиента и индивидуальная инструкция;
- единая история сообщений;
- ручное тестовое входящее и исходящее сообщение;
- дедупликация email/телефона/Telegram внутри playbook;
- кнопки «Запустить агента» и «Остановить агента»;
- при остановке входящие получают статус ожидания.

Локальная приёмка:

- создать два playbook;
- создать лиды с одинаковым email в одном playbook — дубль не создаётся;
- тот же email в другом playbook — отдельная карточка разрешена;
- переместить карточку стадией и через меню;
- остановить playbook и убедиться, что тестовое входящее осталось в ожидании.

### Фаза 2 — навык продажи и документы (3–5 дней)

Делаем:

- мастер настройки продукта, тона, целей, ограничений и квалифицирующих вопросов;
- загрузка DOCX, PDF, PPTX;
- извлечение и предпросмотр текста;
- grounded-ответ: факты только из материалов playbook;
- генерация черновика коммерческого предложения;
- ссылки на использованные документы внутри результата.

Локальная приёмка:

- загрузить по одному файлу каждого формата;
- задать вопрос, отсутствующий в документах — агент честно сообщает, что данных нет;
- получить черновик КП по карточке клиента.

### Фаза 3 — Telegram (3–5 дней)

Делаем:

- подключение Bot Token с проверкой;
- локальный long polling worker;
- production webhook позже;
- входящие создают/обновляют карточку и диалог;
- исходящие сначала создаются как черновики;
- approve/reject/edit перед отправкой;
- retries и журнал доставки.

Локальная приёмка:

- написать тестовому боту;
- увидеть карточку и сообщение;
- подтвердить ответ и получить его в Telegram;
- остановить playbook, написать снова и увидеть сообщение в ожидании.

### Фаза 4 — email (5–7 дней)

Делаем:

- IMAP для входящих и SMTP для исходящих;
- проверка соединения;
- threading через `Message-ID`, `In-Reply-To`, `References`;
- HTML/plain text, вложения и подпись;
- исходящее первое письмо из карточки;
- локальная безопасная почта через test mailbox или GreenMail.

Локальная приёмка:

- входящее письмо создаёт/обновляет лид;
- ответ остаётся в том же треде;
- повторная доставка одного Message-ID не создаёт дубль;
- подтверждённый черновик уходит, неподтверждённый — нет.

### Фаза 5 — автоматизация продаж (4–6 дней)

Делаем:

- структурированное извлечение имени, компании, email, телефона и Telegram;
- обновление только с confidence и журналом изменений;
- классификация стадии;
- автоматический переход в «Идёт общение» и «Клиент хочет заказать»;
- квалифицирующие вопросы;
- режимы `DRAFT_ONLY`, `APPROVAL_REQUIRED`, `AUTO`;
- ручной takeover менеджером.

### Фаза 6 — импорт и массовый запуск (3–5 дней)

Делаем:

- CSV/XLSX-шаблон;
- preview перед импортом;
- нормализация и отчёт о дублях;
- отдельная карточка на контакт;
- очередь первых email;
- дневные лимиты, интервалы, quiet hours, stop campaign.

### Фаза 7 — production hardening (5–8 дней)

Делаем:

- Redis/BullMQ workers, retries, dead-letter queue;
- шифрование секретов;
- audit log;
- health checks и счётчики ожидающих сообщений;
- резервное копирование;
- тест нагрузки и восстановление после рестарта;
- при росте нагрузки — миграция CRM-части с SQLite на PostgreSQL.

## Локальный контур

- `http://localhost:3000` — Next.js UI/API
- SQLite — данные MVP
- `docker compose up -d redis` — очередь с фазы Telegram
- отдельный `npm run crm:worker` — Telegram/email/outbox worker
- Telegram — long polling, публичный tunnel не нужен
- email — test mailbox/GreenMail, реальные клиенты не получают тестовые письма

После каждой фазы пользователь получает:

1. локальный URL;
2. тестовые учётные данные/данные без секретов;
3. короткий чек-лист проверки;
4. список известных ограничений;
5. production-деплой только после явного подтверждения.

## Что не делаем в первом MVP

- произвольные userbot-рассылки в Telegram;
- скрытый обход антиспама и лимитов;
- полностью автоматические массовые отправки без approval;
- сложную настраиваемую воронку до проверки базовых пяти стадий;
- интеграции со сторонними CRM до стабилизации собственной карточки и диалогов.

## Оценка

- локальный рабочий MVP: 2–3 недели;
- Telegram + email + approval: ещё 2–3 недели;
- массовые кампании и production hardening: ещё 2–3 недели;
- полный безопасный первый релиз: ориентировочно 6–9 недель поэтапной работы.

## Следующий шаг

Начать с фазы 1: добавить схему CRM, API, навигацию, канбан и локальные тестовые сообщения. Внешние токены и пароли на этом этапе не нужны.
